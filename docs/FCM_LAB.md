# FCM 喚醒實驗（2026-11-19）

目的：驗證「接收端 App 沒開著」時，能不能用 FCM 高優先級資料訊息叫醒它，作為「手機對手機互傳不用常駐」的第一步。

## 結果（使用者在自己的手機上實測）
- App 在背景：瞬間收到。
- App 從最近工作清單滑掉：**一開始收不到**。原因是手機系統（看起來是小米／HyperOS 類）把滑掉當成強制停止，並拒絕了好幾次「自啟動」。
- 把 Vertex 的「**自啟動**」打開之後：滑掉、鎖屏都收得到，延遲大約幾百毫秒。
- 結論：**技術上可行，但使用者必須在手機上開「自啟動」（並把電池設成無限制）**；不同廠牌名稱與成功率不同，別人的手機不保證。

## 這次實驗的做法（實驗程式不在 main，在 `claude/project-review-continue-qsyt5j` 分支的 commit 9371c41）
- Firebase 專案由使用者自己建（Spark 免費方案），`google-services.json` 在執行時由使用者選檔，存 App 私有資料夾，不進 repo、不用 google-services 外掛。
- 發送端用服務帳戶金鑰簽 JWT 換 access token，呼叫 FCM HTTP v1 送 `priority: high` 的 data 訊息；用完要刪金鑰。
- 接收端 `FcmLabService` 收到就跳通知並寫 `LifeLog`（含延遲、原優先級與實際優先級）。

## 還沒做／要決定
- 這只證明「叫得醒」。互傳要再接：A 臨時開接收服務 → 推播告訴 B「A 在這個位址等你」→ B 被叫醒後連過去拿。推播只當門鈴，真正驗證仍用配對簽章，不能把推播當授權。
- 金鑰：個人使用可放發送端手機（用 Android Keystore 加密）；要給別人用就要有雲端代發（要查費用與方案）。
- 要在 App 裡教使用者開「自啟動」與電池無限制，並偵測收不到的情況。
- 高優先級推播有配額；每次喚醒最好都有使用者看得到的通知。
- 只在同一個區網有效（檔案仍走區網直連）。

狀態：🟡 實驗成功；正式功能尚未開始。

## 階段 2 結果（2026-11-20，實驗版第 705 次執行）
✅ 使用者實測成功：發送端按「門鈴」→ 接收端（App 已滑掉）被叫醒 → 驗證通過 → 用現有簽章請求取回檔案，存到 `下載/PhoneAI/`。

過程中踩到的問題（正式版要避免）：
1. **FCM 資料欄位不能叫 `from`**（保留字，HTTP 400）。門鈴欄位改叫 `src`；`DoorbellTest` 有測試擋保留字。
2. **「本機位址」要用 Wi-Fi 網路的，不能掃所有介面**（行動數據／VPN 也可能是私有位址）。用 `ConnectivityManager` 只看 `TRANSPORT_WIFI`，需要 `ACCESS_NETWORK_STATE`。
3. **同網段判斷要用實際的前綴長度**，不能固定 /24（使用者的 Wi-Fi 位址是 172.23.x.x，不同 /24 仍可能在同一網路）。`Doorbell.sameSubnet` 支援「位址/前綴」。
4. **互傳伺服器不一定在跑**：系統（小米）會把它收掉，使用者原本得兩邊都開介面才傳得動。發送端按門鈴前要先 `TransferService.start` 並等它 `running`；用完要關（階段 3 要做）。
5. 驗證失敗要讓人看得到原因：實驗版用通知顯示；正式版只寫記錄，但要有「測試推播」與診斷畫面。

下一步（階段 3）：設定頁（選兩個檔案、狀態、測試、刪金鑰）、金鑰用 Keystore 加密、用完自動關伺服器、`file_send` 接上（助理找檔案並讓使用者選）、自啟動與電池的引導、token 在配對時自動交換，之後再決定何時把 Firebase 依賴併進 main。
