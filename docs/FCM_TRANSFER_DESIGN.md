# 手機對手機互傳：用 FCM 當「門鈴」的設計（草案）

> 狀態：📝 設計草案。階段 1 的純邏輯（`Doorbell`：產生、加解密、驗證、位址與欄位檢查）與單元測試已完成（2026-11-19），**尚未接上 Firebase 與 UI**；Firebase 依賴與接收服務等確定要併進 main 時再加。前提是 `docs/FCM_LAB.md` 的實驗結果（背景、滑掉、鎖屏都能被叫醒，延遲約幾百毫秒；**需要使用者開「自啟動」**）。
> 本文件建立在現有互傳（`docs/FILE_TRANSFER.md`：配對、HMAC 簽章、AES-GCM、`TransferServer`／`TransferClient`）之上，**不改現有協定**。

## 1. 目標與不做的事
目標：兩支都不常駐的手機，在同一個區網裡，A 說「把 X 傳到 B」，B 沒開 App 也會自己去拿。
不做：
- 不讓手機常駐（沒有常駐前景服務）。
- 不傳檔案內容經過 Google／FCM（FCM 只傳小訊息）。
- 不改現有配對與傳輸的加密、簽章。
- 不做遠端（不同網路）；`TransferStore.isTailnet` 顯示專案已有 Tailscale 位址的處理，之後可評估是否延伸，**這次不碰**。

## 2. 流程（A 傳給 B）
1. A 的 App 在使用中（你正在對助理說話），所以 A 可以**臨時**啟動 `TransferServer`（現有，原本是總開關開著才跑）。
2. A 用 FCM 向 B 送一則**高優先級資料訊息**（內容見 §4），這就是門鈴。
3. B 的系統叫醒 B 的 `FcmReceiverService`；它**先驗證訊息**（§5），通過才繼續，並顯示一則通知「正在接收來自 A 的檔案」。
4. B 啟動短暫的前景服務（FCM 高優先級是系統允許的例外），用**現有的簽章請求**向 A 取檔：`GET /v1/file?path=…`（B 是客戶端，A 是伺服器）。
5. 檔案存到 B 的 `Download/PhoneAI/`（現有收件位置），完成通知，B 結束服務。
6. A 看到取檔完成（或逾時）就關掉臨時的 `TransferServer`。

方向說明：永遠是「被叫醒的一方去拉」，所以只有 A 需要臨時開伺服器，B 只要是客戶端，不需要常駐監聽。

## 3. 一次性設定
每位使用者自己建 Firebase 專案（Spark 免費方案），只有自己的裝置會註冊進去。
1. 在 Firebase 建專案、新增 Android App（套件名稱 `com.phoneai.overlay`）、下載 `google-services.json`。
2. 在 App「設定 → 互傳檔案 → 推播喚醒」選這個檔案（存私有資料夾，不進 repo，沿用實驗版做法）。
3. **發送端**（要能叫醒別人的那支）另外選服務帳戶金鑰 JSON；App 立刻用 Android Keystore 的 AES-GCM 金鑰加密後存，**刪掉明文**，並提示使用者刪除下載資料夾的原檔。
4. 配對時（現有流程）**順便交換 FCM token**，存進 `transfer_peers.json` 對應的 Peer；token 變了（`onNewToken`）就在下次連線時更新。
5. App 檢查並引導：通知權限、電池「無限制」、**自啟動**（依廠牌顯示對應路徑；偵測不到就文字說明）。

## 4. 門鈴訊息（FCM data，`priority: high`）
- 內容（JSON）：`v`（版本）、`from`（A 的裝置 id）、`ts`（毫秒時間戳）、`nonce`（隨機）、`ip`／`port`（A 目前的區網位址）、`path`（要拿的檔案）、`name`、`size`，密文用 AES-GCM（金鑰＝HMAC(配對金鑰, "bell|"+nonce)，每則一把新的；AAD 綁住 v、from、ts、nonce，GCM 的標籤同時負責完整性，所以不另外附 HMAC）。實作：`Doorbell.java`（純 Java）與 `DoorbellTest`。
- 大小遠小於 FCM 限制（約 4 KB）。
- 不放任何金鑰或可直接使用的授權；它只是「請你去這裡拿這個」。

## 5. 接收端驗證（任何一項不過就丟掉，不連線、不通知）
1. `from` 是已配對的裝置，且有對應金鑰。
2. HMAC 與解密都通過。
3. `ts` 與現在相差 ≤ 60 秒；`nonce` 沒出現過（記錄最近的，沿用現有防重送）。
4. `ip` 是私有區網位址（`10.*`、`172.16–31.*`、`192.168.*`），且與 B 目前所在網段合理；不是就丟掉。
5. 檔案大小 ≤ 2 GiB，空間足夠（沿用 `SpaceReserver`）。

為什麼要這麼嚴：
- 如果偽造的門鈴能讓 B 對攻擊者的位址發出**簽章過的** `GET`，攻擊者可能在 30 秒內重送給真正的 A，拿走他自己指定的檔案。所以門鈴本身必須被驗證，且**取檔請求只送到驗證過的位址**。
- 發送端要有服務帳戶金鑰才能發推播；即使金鑰外洩，沒有配對金鑰也做不出能通過驗證的門鈴。

## 6. 金鑰與隱私
- 服務帳戶金鑰只在發送端，加密存放；設定頁有「刪除金鑰」。
- 這個金鑰只屬於使用者自己的專案，專案裡只有他的裝置，外洩的影響範圍有限，加上 §5，最糟情況是接收端被吵醒、跳一則通知。
- Google 會看到推播的時間與收發雙方的 token（內容加密）。
- 之後若要給不想自己建專案的人用，才需要雲端代發（要查方案與費用），**不在這次範圍**。

## 7. 失敗情況與處理
| 情況 | 處理 |
|---|---|
| B 收不到門鈴（自啟動沒開、省電限制） | A 等待 N 秒（暫定 20）沒人來取，就提示「對方沒有回應，請確認對方的自啟動與電池設定」；提供「測試推播」鈕（沿用實驗畫面） |
| B 與 A 不在同網段 | B 驗證失敗，A 逾時提示 |
| A 的 IP 變了／在訊息之後才變 | 門鈴帶最新位址；失敗就逾時提示 |
| token 過期或不存在 | FCM 回 `UNREGISTERED`，標記該 Peer 需要重新配對或更新 token |
| 推播被降級（配額用完） | 顯示延遲；每次都帶可見的通知，避免被降級（Google 的建議） |
| 傳到一半斷線 | 沿用現有行為：刪暫存檔、不留半個檔案 |

## 8. 要改的程式（預估，分小步）
1. `FcmTransfer`（新）：金鑰庫加密存放、發送門鈴（沿用實驗版的 JWT 流程）。
2. `FcmReceiverService`（新）：驗證、顯示通知、啟動短暫前景服務；服務類型沿用現有 `specialUse`。
3. `TransferStore.Peer` 加 `fcmToken`；配對流程交換 token。
4. `FileTools`：`file_send` 在對方未開伺服器時改走「推播＋臨時伺服器」；現有直連路徑保持原樣。
5. 設定頁「推播喚醒」：選兩個檔案、狀態、測試、刪金鑰、權限引導。
6. 測試（純 JVM）：門鈴的加密與驗證（過期、重放、錯金鑰、非私有位址、大小超限）；Peer 的 token 更新。

## 9. 分階段
1. **階段 1（最小）**：只做門鈴驗證與「B 被叫醒後顯示通知」，不取檔，用單元測試涵蓋驗證邏輯。
2. **階段 2**：B 被叫醒後真的去 A 取檔；A 臨時開伺服器。
3. **階段 3**：設定頁與權限引導，並把 `file_send` 接上。
4. 每階段都先在分支與 CI 驗證，使用者在手機上實測後才併進 `main`。

## 10. 還沒決定／還沒查證
- A 臨時開 `TransferServer` 的前景服務類型與時長（A 是使用中，應該不受背景限制，但要實測）。
- 服務帳戶金鑰用 Keystore 加密後，備份與換機時的行為。
- B 的前景服務由 FCM 啟動後，`specialUse` 在新版 Android 的限制（官方文件沒有明說，要實測）。
- 不同廠牌「自啟動」的引導文字與偵測方式（目前只在使用者的手機實測過）。
- 要不要把 `ip` 以外的探索（現有 UDP 探索）併進來作為備援。
